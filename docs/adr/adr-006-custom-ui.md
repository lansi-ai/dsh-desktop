# ADR-006 · UI 路线：Desktop-First 自绘界面（主面不复用官方 Web UI）

状态：**已启用（2026-08-27 · D-20 全量自绘决策）** · 关联：[`13-ui-design.md`](../13-ui-design.md)、ADR-007

## 启用记录（2026-08-27）
用户决策「C. 全量自绘」+ 排期插队（自绘优先于 M4 分发）。执行策略 = **逐槽位替换**（非一次性切换）：
M6-P1 布局骨架已落地（M3-c：`@lansi-ai/dsh-desktop-layout` + `dsh-desktop-titlebar`），
后续 P2 外壳小件 → P3 侧栏 → P4 对话主区 → P5 过程可视化 → P6 设置底座，
每阶段可用可验证，官方 `ui-*` 插件经 `CLIENT_EXCLUDE_IDS` 逐个排除。见看板 M6 节路线图。

## 背景
原 L2 路线（官方 Web UI dist 原样复用）在用户试用反馈后有「太难用」的诉求；但用户确认**本轮不考虑修改 UI 设计，先做成 desktop**。
因此本 ADR **降级为暂缓/可选**：主线继续 L2（官方 UI 复用），自绘 UI 作为未来升级位保留。

## 决策
- **（暂缓）主面 = 自绘 Desktop UI**（自有组件树、自有设计 token、键盘优先/命令面板/Spotlight/多窗口原生交互），
  复用官方 **Host 内核与协议**（同一 Cordis Host、同一四象限 IPC 载波、同一会话/工具/审批语义）；
- **（暂缓）官方 Web UI 降级为可选「兼容窗口」**（默认关闭，仅承载依赖官方槽位的旧 client 插件与管理面）；
- 采用**渐进式自绘**：M1 先做对话流最小集，管理面初期由兼容窗口承载，逐波迁移。
- **（当前主线）** 官方 Web UI 发行物作为 renderer（L2）；自绘 UI 在 M5+ 或用户明确要求时再切换（宿主与协议不变）。

## 理由
1. 用户诉求明确（差异化样式）是产品决策的输入；浏览器式布局与桌面心智冲突是真实体验问题；
2. 「非套壳」的本质是**宿主内嵌 + 能力插件化 + 协议共用**——这三者并不依赖「复用官方 dist」；
   自绘 UI 只是替换「浏览器壳与槽位」，核心主张不变（ADR-001/002/003 继续有效）；
3. 渐进迁移把「重做全部管理面」的成本摊到多波，M1 成本与 L2 相当（自绘对话流 ≈ 搭 dist 的工程量）；
4. 官方协议契约（`api/rpc.ts`、帧流、`approval`）是我们的数据层——自绘 UI 与官方 Web 在**数据语义上完全一致**，
   未来官方 UI 改进或切换皮肤成本低。

## 后果
- 需要自研 renderer 项目（vite + React + 自有组件库）与自有 client 插件契约（新槽位）；
- 官方 client 生态插件（含用户现有三个插件）不能直接渲染 → 兼容层是刚需（ADR-007）；
- 不再依赖 `BootSeams`/官方 client 加载链（R5 风险降级），改为自己的 UI 装载路径；
- `dsh-ui://` 协议服务于**自研 UI 产物**；官方 dist 仅供兼容窗口。

## 备选否决
- 继续 L2（官方 dist 复用）：体验诉求不满足
- 完全 L3（SDK + 全自绘，弃官方 client 机制）：成本过高且短期内管理面缺失（见 [03-routes.md](../03-routes.md) Route C）

## 复查触发
自绘 M1 对话流完成后用户试用；官方 Web UI 大版本改版时。
